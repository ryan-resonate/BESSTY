BESS group / array creator

Two scenes below: (1) the wizard modal that opens when the user clicks + BESS group, and (2) the on-map representation of a placed group with the rotation + drag affordances. Static mockup — no working code; meant for a design pass before we lock in the data model.

Scene 1 · Wizard modal

Opens on + BESS group (a new button in the Sources tab next to "+ BESS"). Also re-opens via Edit group in the right-click menu shown in Scene 2. Left half = parametric form (the "row sequence"); right half = live top-down preview of what the layout will materialise as. Each "Row" in the sequence is one horizontal line of units; rows execute top-to-bottom in the group's local coords (rotation applies to the whole thing). Each row has a pattern (e.g. "BESS BESS BESS Inverter") and a repeat count for that pattern within the row, plus its own gap-after to the next row — so "two close rows, then a wide gap, then two more rows" is just a different gap-after on each row.

Scene 2 · On-map view (placed group, selected)

Once applied, the group appears on the map as a translucent bounding rectangle with the individual units inside. When the group is selected: a rotation handle floats above the top edge, a translate handle sits in the middle, and corner handles let you scale the row spacing proportionally (alt-drag for free corners). Right-click anywhere on the group opens the contextual menu shown. Double-clicking the group re-opens the wizard from Scene 1 with the saved parameters.

Corner handles
Drag to proportionally scale row spacing. Alt-drag a corner for free scaling. Use the wizard for precise per-row numbers.

Open design questions to flag

  1. Is the row sequence model (each row has its own pattern + repeat + gap-after) flexible enough for what you've described, or do you need a higher-level "block" abstraction (e.g. "BESS+INV block ×3, then gap, then BESS+INV block ×2")?
  2. Should the preview update live as the user edits the form, or only on an explicit "Refresh preview" button? Live is friendlier but means a recompute on every keystroke.
  3. For parametric editing after Apply, when the user re-opens a group and changes parameters: should per-unit edits made on the map (e.g. dragged one BESS 3 m east for a fence clearance) be preserved across regeneration (and rendered as a small "modified" chip), or discarded with a warning?
  4. Bake to individual sources (in the right-click menu) — should this be exposed? It's a one-way decommit that converts the group's sources to standalone, losing parametric editing. Useful escape hatch for projects where the array layout becomes too irregular for the parametric model.
  5. For the auxiliary pattern, is "insert 1 INV after every N BESS within a row" the right primitive, or do you want freer composition (e.g. alternating BESS / TX / BESS / INV)? The current mockup uses the freer "explicit unit list per pattern" approach, which subsumes the N-per-block case.
